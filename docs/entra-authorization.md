# Entra ID のロールによる認可: 設定手順と運用

このアプリは、Entra ID の割り当て（App Role またはグループ）を **アプリ内ロール** に変換し、ログインのたびに利用者へ保存します。ロールを 1 つも持たない利用者はログインできません。保存されたロールに基づいて、画面と操作の可否を判定します。

ここでは、Entra ID 側で必要な設定、ロール取得方式の選び方、運用上の制約と事前確認をまとめます。ログイン（認証）の設定は `entra-authentication` 側の手順書を参照してください。

> Entra 管理センターの画面名や項目名は、Microsoft の更新で変わることがあります。ここでは 2026 年時点の呼称で書いています。

## 1. 方式の選び方

ロールの取得方式は 2 つあり、設定（`authorization.role_source`）で 1 つを選びます。選ぶ基準は **テナントの契約種別** です。

| 方式 | 設定値 | 使うテナント | 仕組み |
|------|--------|--------------|--------|
| roles クレーム方式 | `roles` | Entra ID P1 / P2 | アプリに割り当てた App Role の値が ID token の `roles` クレームに入る |
| groups クレーム方式 | `groups` | Free | ID token の `groups` クレーム（グループの Object ID）を、設定した対応表でロールへ変換する |

- App Role の **定義** は Free / P1 / P2 のいずれでも行えます。ただし、エンタープライズアプリへの **グループ単位の割り当て** は P1 / P2 が必要です。Free ではユーザー単位の割り当てになります。
- groups 方式は Free でも使えますが、グループ数の上限（後述の overage）に制約があります。
- 迷ったら、P1 / P2 のテナントでは roles 方式を選んでください。overage が起きず、事前確認も不要です。

どちらの方式でも共通の規則が適用されます。

- コードで定義されたロール（`app/models/role.rb` の `Role::NAMES`）だけが有効です。定義にないロール、対応表にないグループは無視されます。
- 有効なロールが 1 つもなければ、ログインは拒否されます。
- ロールはログインのたびに **全置換** されます（追加ではなく、その時点の割り当てが正です）。

## 2. アプリ内ロール名

有効なロール名は `app/models/role.rb` の `Role::NAMES` で定義します（現在は仮の `admin` / `member`。最初の業務機能で確定します）。

- Entra ID の App Role の **値**、および groups 方式の対応表のロール名は、`Role::NAMES` の名前と **大文字小文字を含めて完全一致** させてください。一致しないものは無視され、結果としてログインが拒否されることがあります。
- ロール名をコードから消した場合、その名前で保存済みのロールは効かなくなります（権限判定の前に定義済みロールだけへ絞り込むため）。

## 3. roles クレーム方式（P1 / P2）

### 3.1 Entra ID 側の設定

1. **アプリの登録**（このアプリ）で **アプリ ロール** を作成します。
   - 表示名は任意、**値** は `Role::NAMES` のロール名と完全一致させます。
   - 許可されるメンバーの種類は「ユーザー/グループ」にします。
   - 有効化します。
2. **エンタープライズ アプリケーション**（同じアプリ）を開き、**ユーザーとグループ** で、グループ（またはユーザー）にアプリ ロールを割り当てます。
3. エンタープライズ アプリケーションのプロパティで **割り当てが必要ですか？** を **はい** にします。
   - これにより、割り当てのない利用者は Entra ID 側でサインインできなくなります。
4. トークン構成の追加設定は不要です。割り当てられた App Role の値が、`roles` クレームとして ID token に入ります。

### 3.2 特徴と注意

- アプリに割り当てた App Role だけがクレームに入るため、**overage は起きません**。
- **グループの階層構造は反映されません。** App Role が割り当てられるのは、割り当てたグループの直接のメンバーです。入れ子のグループ（グループの中のグループ）のメンバーには、ロールが付きません。階層を使いたい場合は、必要なグループそれぞれに割り当ててください。
- 1 人の利用者に複数のロールが付いた場合、そのすべてが保存され、権限は和集合になります。

## 4. groups クレーム方式（Free）

### 4.1 Entra ID 側の設定

1. **アプリの登録** の **トークン構成** で **グループ クレームを追加** します。
   - グループの種類は **セキュリティ グループ** を選びます。
   - トークンの種類は **ID** に付けます。
   - 出力形式は **グループ ID**（既定の Object ID の GUID）のままにします。名前や sAMAccountName 形式は使えません。
   - 「アプリケーションに割り当てられているグループ」への絞り込みは P1 / P2 でしか使えないため、Free では選べません。所属するセキュリティ グループがすべてクレームに入ります。
2. ロールに対応させたいグループの **Object ID** を控えます（Entra 管理センター → グループ → 対象のグループ → 概要 → オブジェクト ID）。

### 4.2 アプリ側の設定（対応表）

グループの Object ID とロール名の対応を、設定ファイルに書きます。キーはグループの Object ID（GUID）、値は `Role::NAMES` のロール名です。大文字小文字は区別せずに照合します。

```yaml
# config/settings/production.yml（または git 管理外の config/settings.local.yml）
authorization:
  role_source: groups
  group_role_map:
    "aaaaaaaa-0000-0000-0000-000000000001": admin
    "bbbbbbbb-0000-0000-0000-000000000002": member
```

- 対応表にないグループは無視されます。
- 複数のグループが同じロールに対応していても構いません（ロールは重複なく保存されます）。
- 起動時に、対応表が空、または `Role::NAMES` にないロール名を指している場合、ログに警告が出ます（グループ ID は出力されません）。

### 4.3 overage（グループ数の上限）

JWT では、所属グループが **200 を超える** と、`groups` クレームが ID token から外れ、代わりに `_claim_names` / `_claim_sources` が入ります（overage）。

- このアプリは Microsoft Graph を呼んで解決 **しません**。overage が起きた利用者は **ログインを拒否** し、「所属しているグループの数が多すぎて利用権限を判定できないため、サインインできませんでした。管理者にお問い合わせください。」と表示します。
- グループ数は、入れ子を含めた所属の総数で数えます。
- 利用者に付けるグループ数を絞る（不要なグループから外す）か、roles 方式（P1 / P2）へ切り替えると解消します。

#### 事前確認

groups 方式を有効にする前に、200 グループを超えて所属している利用者がいないかを確認してください。たとえば Microsoft Graph PowerShell では、次のように所属数を数えられます。

```powershell
# 対象ユーザー 1 人の入れ子を含むグループ所属数
(Get-MgUserTransitiveMemberOf -UserId <ユーザー ID または UPN> -All | Where-Object { $_.AdditionalProperties.'@odata.type' -eq '#microsoft.graph.group' }).Count
```

- 全ユーザーを対象にする場合は、ユーザー一覧に対して繰り返し実行し、200 に近い、または超える利用者を洗い出します。
- 新しい利用者やグループの追加で、後から超える場合があります。定期的に確認してください。

## 5. 設定キー

`config` gem の設定で切り替えます（環境変数による上書きは有効にしていません）。

| キー | 値 | 必須 | 説明 |
|------|----|------|------|
| `authorization.role_source` | `roles` / `groups` | **はい** | ロール取得方式。**既定値はありません**。未指定や未対応の値ではアプリが起動しません |
| `authorization.group_role_map` | `{ グループ Object ID: ロール名 }` | groups 方式のみ | グループとロールの対応表 |

- 共通の設定は `config/settings.yml`、環境ごとの設定は `config/settings/<環境>.yml` です。`config/settings.local.yml` と `config/settings/*.local.yml` は git 管理外で、上書きに使えます。
- `role_source` は各環境のファイルで明示します。本番環境の既定は `roles` です。Free テナントで運用する場合は `groups` に変更してください。

## 6. ロール変更の反映タイミング

- ロールは **ログイン時にだけ** 更新されます。Entra ID 側で割り当てやグループを変更しても、利用者が **次にログインするまで** アプリには反映されません。
- 反映の遅れの上限は、`entra-authentication` のセッションの **絶対時間上限**（`ENTRA_SESSION_ABSOLUTE_HOURS`、既定 8 時間）です。この時間を超えるとセッションが失効し、再ログインで最新の割り当てが取り込まれます。
- 割り当てを取り消した人を、すぐに使えなくしたい場合は、Entra ID 側でアカウントの無効化・セッションの失効を行い、必要ならこの上限を短くしてください。

## 7. ログイン拒否と運用時の確認

ロールに起因してログインが拒否されると、利用者はログイン画面へ戻り、理由を示す文言が表示されます。

| 理由 | 表示の趣旨 | 主な原因 |
|------|------------|----------|
| ロールなし（`no_roles`） | 権限が割り当てられていないためログインできない | 割り当てがない / 定義にないロールのみ / groups の対応表にないグループのみ / 方式と Entra ID 側の設定の不一致 |
| overage（`groups_overage`） | グループが多すぎて判定できない | groups 方式で所属グループが 200 を超えた |

運用者はアプリケーションログで、拒否の理由と対象を確認できます。

```
[authorization] login rejected reason=no_roles user_id=42
```

- クレームの内容、グループ ID、ロール名はログにも画面にも出しません。
- 拒否が続く場合の確認順序: (1) `role_source` が Entra ID 側の設定と合っているか、(2) App Role の値または対応表のロール名が `Role::NAMES` と完全一致しているか、(3) roles 方式なら割り当てが「グループの直接のメンバー」になっているか、(4) groups 方式ならトークン構成のグループ クレームが有効で、グループが対応表に載っているか。

## 8. 権限なしの扱い

ログイン済みの利用者が、許可されていない画面や操作にアクセスすると、権限がない旨の画面（HTTP 403）が表示されます。ロール名や権限の定義は画面に出ません。ロールを持たない状態でセッションだけが残っている場合は、すべての操作が拒否されます。

権限の定義は `app/models/ability.rb` にあります。業務機能を追加するときは、そのリソースに対する権限をロールごとに追記し、コントローラでは操作の前に `authorize!`、ビューでは `can?` で判定してください。

## 9. 導入時のチェックリスト

- [ ] `Role::NAMES` のロール名を決めた
- [ ] 方式（`roles` / `groups`）を契約種別に合わせて選び、各環境の `authorization.role_source` に設定した
- [ ] （roles）App Role の値が `Role::NAMES` と完全一致している。グループをエンタープライズアプリに割り当てた。「割り当てが必要ですか？」を「はい」にした
- [ ] （groups）グループ クレーム（セキュリティ グループ、グループ ID、ID token）を有効にした。`group_role_map` に対応を登録した
- [ ] （groups）200 グループを超えて所属する利用者がいないことを確認した
- [ ] ロールを持つ利用者と持たない利用者の両方で、実際にログインを試して挙動を確認した（この確認は実際の Entra ID テナントで人が行う）
